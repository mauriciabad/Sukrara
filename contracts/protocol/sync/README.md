# Protocol sync fixtures

Owner → follower event sequences for Nostr protocol v2 ([PROTOCOL-v2.md](../PROTOCOL-v2.md)), with the verdict each
event must get and the follower state the sequence must leave. Both apps replay them: Android
`apps/android/core/protocol` `SyncFixturesTest` / `IdentityConflictTest`, Mac `SyncFixtureTests`. Keys are throwaway
test keys (the OGS draft-1 vector keys plus `D2` = sha256("sukrara/sync/D2")); all glucose data is synthetic.

| file | what it pins |
|---|---|
| `join-readings.json` | key delivery → roster → hour chunk → live (reading + sensor) → reading-less sensor update → outsider rejected |
| `treatments-writer.json` | writer scope: wearer entry, writer's own entry and edit, writer hijack rejected, wearer tombstone, older `(u,o)` ignored |
| `settings-mirror.json` | mirrored settings: newest `u` wins, only from a roster device |
| `rotation.json` | phone change / revoke: epoch 2 with a new device, old device and old epoch rejected, late epoch-1 roster ignored. Also the identity-restore case (same wire sequence: new device key, new epoch delivered to every follower, roster with only the new device); Mac `ProtocolCompatTests` replays it through the runtime |
| `owner-conflict.json` | A3, owner side: the wearer's own echoes, its own rotation and late old events are `fine`; a newer roster or backup from another app publishing as the same identity is a `conflict` |

## Format (`v` 1)

The fixtures carry the real signed, encrypted events (not decrypted payloads), so every acceptance rule — signature,
roster membership, epoch, decryption, tags — runs on both platforms exactly as it does on relays and Bluetooth.

Follower sequences: `keys` (`{name: {sec, pub}}`), `sid`, `follower` (key name), `identity` (I's pub), `now` (unix s,
the clock for every step), `events` (`{step: nostr event}`), `steps` (`[{event, expect}]`, `expect` =
`accepted|rejected|ignored:<what>`, the reference follower's codes), `expected`:

- `status` (`new|requested|active|declined|inviteused|revoked`), `epochs` (sorted), `devices`, `writers`;
- `readings`: `[t, sgv, rate|null]` sorted by `t`, first reading per `t` kept;
- `sensor`: `{ss, se, sw}` from the newest live event (`null` when none or cleared);
- `treatments`: `[{id, k, a, u, o, del}]` sorted by `id`, merged by `(u, o)` (a wearer entry overrides a forged writer copy);
- `settings`: `{u, graph}` of the newest accepted settings, or `null`; `alerts`: count accepted.

`owner-conflict.json`: `marks` (what the wearer's phone persists: its identity, its device key, the epochs it holds,
`lastRosterAt` / `lastBackupAt` = `created_at` of the last roster / backup it published), `events`, `checks`
(`[{event, expect}]`, `expect` = `fine` | `conflict:<RosterFromOtherDevice|RosterUnknownEpoch|BackupFromElsewhere>`).

## Changing them

Generated by the Android tests with `-Dsukrara.regen=true` (events are re-encrypted with fresh NIP-44 nonces; the
`steps` and `expected` must not change unless the spec changed — then the Mac lands in the same change). Cross-checked
2026-10-27 against the independent Python reference (`poc/spec/reference`, its own secp256k1 / NIP-44 code):
`join-readings` and `treatments-writer` give the same verdict at every step and the same final state. `rotation`
agrees except `roster-1-refresh` / `live-before-roster-2`: the Sukrara apps (PoC `FollowerEngine` and V1) let a newer
epoch's key outrank every older-epoch roster, while the reference still takes the replaced phone's refreshed roster
and then rejects the new phone's reading — the apps' rule is the safe one and is what these fixtures pin.
`settings-mirror` differs only because that reference predates the settings rule (it answers `ignored:unknown-30078`).
